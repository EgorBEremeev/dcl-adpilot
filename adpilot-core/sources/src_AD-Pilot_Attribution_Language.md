### 1. Определение DCL: AD-Pilot Attribution Language

**AD-Pilot DCL** — это предметно-ориентированный язык управления контекстом LLM-агентов в задачах цифровой инвентаризации, атрибуции и листинга. Он формализует процесс трансформации разрозненных данных (Draft_Record) в верифицированный цифровой актив (Item_Record), пригодный для мультиканальной дистрибуции. Концепция DCL когнитивных Линз реализует выявления скрытых свойств товара, обеспечивая переход от хаотичного описания к структурированной мастер-записи.

**Методологический принцип:** Язык опирается на `Трехосевую модель атрибутов`, в которой атрибуты товара — это не плоский список характеристик, а векторы в трехмерном пространстве Критичность, Объективность, Происхождение. Такой подход позволяет LLM формировать динамическую модель товара в зависимости от контекста конкретного экземпляра, рынка, целей и канала продажи, и других переменных факторов.

### 2. Сущности (Entities / Operands)

Сущности — это объекты, над которыми производятся операции. В AD-Pilot DCL они представляют этапы эволюции данных о товаре.

| Сущность DCL (`Entity`)          | Описание                                                                                                                                                                                                                                  | Роль                                       |
|:---------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------|
| **`Draft_Record`**               | Пользовательский текст (короткое, хаотичное описание, «шум»).                                                                                                                                                                             | Входной материал (Source).                 |
| **`Market_Context_Fingerprint`** | Возможно полное информационное поле товарной категории. Специфика данной категории товаров. Максимально  исчерпывающий контекст, необходимый для понимания того, как этот тип товаров производится, регулируется, продается и выбирается. | Промежуточный артефакт для настройки Линз. |
| **`Attribute_Schema`**           | JSON Schema с мета-тегами 3-осевой модели. Эволюционирует от "Кора" к полному дереву.                                                                                                                                                     | План данных (Blueprint).                   |
| **`Item_Record`**                | JSON объект, соответсвующий `Attribute_Schema` и заполненный фактами из `Draft_Record` с соблюдением *Closed-World Assumption*.                                                                                                           | Источник истины (Master Data).             |
| **`Channel_Listing`**            | Карточка товара (описание + спецификация), адаптированная под конкретный маркетплейс.                                                                                                                                                     | Финальный продукт (Export).                |

### 3. Операции (Operations / Verbs)

Операции определяют когнитивное действие, которое агент выполняет над Сущностью.

| Операция DCL (`Operation`) | Семантика действия | Реализуемый сценарий |
| :--- | :--- | :--- |
| **`INFER`** | **Анализ и Классификация.** Извлечение неявного контекста из сырого текста. Определение, к какому классу относится объект. | *Фаза 1: Определение Контекста.* |
| **`DEFINE`** | **Создание (Instantiation).** Генерация первичной жесткой структуры (Конституции) на основе контекста товара. Работает с атрибутами на пересечении ТРЕХ осей: [L1.1 Criticality: Constitutional] + [L2.1 Objectivity: Factual] + [L3.1 Origin: Inherent]. | *Фаза 2: Создание Канонического Кора.* |
| **`ENRICH`** | **Обогащение (Mutation).** Наращивание дополнительных слоев атрибутов (L1.2, L2.x, L3.x) на существующую схему путем применения Линз. | *Фаза 3-4: Маркетинговое и Продажное расширение.* |
| **`EXTRACT`** | **Извлечение Фактов.** Заполнение полей `value`. Строгий режим: "Если нет в тексте — null". Запрет галлюцинаций. | *Сценарий 2: Извлечение Атрибутов.* |
| **`ADAPT`** | **Трансформация.** Маппинг атрибутов и генерация текста (Storytelling) под требования внешней системы. | *Сценарий 3: Подготовка карточки.* |

### 4. Линзы (Lenses / Modifiers)

Линзы в AD-Pilot DCL — это проекции Агентов (PIM-архитектора, Социолога, Экономиста, Интегратора). Они инкапсулируют логику 3-осевой модели и знания домена, управляя **вниманием** операторов `DEFINE` и `ENRICH`. Линза не содержит жестко заданного списка атрибутов; она задает эвристики, которые смещают веса Критичности, Объективности и Происхождения данных, заставляя Агента находить и приоритезировать определенные характеристики.

#### 4.1. Методология проектирования Market-Линз (Агент-Социолог)

**Задача PIM-системы:**
В домене PIM (управление информацией о продукте) мы моделируем *информационную потребность* покупателя (чтобы структурировать описание товара), в отличие, например, от домена CRM/AdTech (управление людьми), где мы анализируем *пользователя/лида* (чтобы показать рекламу). Потому социально-демографические признаки (пол, возраст, доход) для PIM не релеванты: они описывают человека, но не диктуют структуру данных товара, которая способствует принятию решения о покупке. Схема атрибутов, ожидаемых 20-летней студенткой-фотографом и 50-летним профессионалом будет идентичной (им обоим нужны технические параметры), в то время как продающие атрибуты товара для двух 40-летних мужчин может кардинально отличаться, если один ищет камеру для работы, а второй — для отпуска.

Для решения этой задачи возможны следующие концептуальные подходы:

**1. Функционально-Ролевая Модель (Functional-Role Model)** — **[ПРИНЯТО К РЕАЛИЗАЦИИ в AD-Pilot]**
Подход, основанный на декомпозиции контекста потребления на 4 ключевых вопроса:
*   **Где? (Geo):** Физические и культурные ограничения среды.
*   **Кто? (Expertise):** Уровень когнитивной нагрузки и глубины знаний.
*   **Как? (Scenario):** Функциональный контекст использования.
*   **Зачем? (Value):** Экономическая мотивация и психология ценности.
*   *Причина принятия:* Универсальность подхода и широкий охват товарных категорий на C2C рынке вместе с простотой интерпретации для продавцов.

**2. Jobs to be Done (JTBD)** — **[Альтернативный подход]**
Концепция Клейтона Кристенсена: "Мы нанимаем продукт, чтобы он выполнил работу". Вместо описания человека, мы описываем его "Работу" (Job).
*   *Суть:* Линзы классифицируются по типу "Работы".
    *   **Lens: Risk Minimization (Минимизация риска).** Задача: "Не совершить ошибку". Фокус внимания смещается на гарантии, совместимость, политику возврата, надежность бренда (L1.3 Trust). Идеально для запчастей, дорогой техники.
    *   **Lens: Self-Expression (Самовыражение).** Задача: "Показать, кто я". Фокус на дизайне, цвете, кастомизации, лимитированных сериях. Актуально для моды, декора, аксессуаров.
    *   **Lens: Resource Optimization (Оптимизация ресурсов).** Задача: "Сэкономить время/деньги". Фокус на КПД, расходе топлива, стоимости владения, эргономике. Актуально для инструментов, коммерческого транспорта.
*   *Причина отказа:* Сложнее для автоматизации (требует глубокого понимания неявной "работы"), менее универсальна для эмоциональных покупок (игрушки). Элементы JTBD частично интегрированы в линзы `Scenario` и `Value`.

**3. Психографическая Модель (Big 5 / OCEAN)** — **[Альтернативный подход]**
Классификация Линз по чертам характера покупателя (Психотипы).
*   *Суть:* Настройка тональности и акцентов схемы под психотип.
    *   **Lens: Conscientiousness (Добросовестность).** Покупатель ищет порядок и предсказуемость. Схема должна быть перегружена точными ТТХ, инструкциями, спецификациями (акцент на L2.1 Factual).
    *   **Lens: Openness (Открытость опыту).** Покупатель ищет новизну. Акцент на уникальных функциях, инновациях, необычном дизайне (акцент на L1.2 Differentiator).
    *   **Lens: Neuroticism (Невротизм/Тревожность).** Покупатель ищет безопасность. Акцент на экологичности, отсутствии вреда, защитных функциях (блокировки, предохранители).
*   *Причина отказа:* Слишком абстрактна для формирования жесткой схемы данных. Трудно однозначно перевести "Тревожность" в конкретное поле JSON (например, "материал корпуса" важен и тревожному, и прагматичному, но по разным причинам). Подходит для Storytelling, но не для PIM.

**4. B2B vs B2C Procurement** — **[Альтернативный подход]**
Разделение по типу процесса закупки.
*   *Суть:* Две жесткие линзы, меняющие набор обязательных полей.
    *   **Lens: B2B.** (Профессиональный закупщик). Фокус: НДС, оптовая цена, артикул производителя, сертификат соответствия, логистические габариты паллеты.
    *   **Lens: C2C.** (Охотник за сокровищами). Фокус: "Торг уместен?", "Причина продажи?", "Наличие коробки", субъективное состояние.
*   *Причина отказа:* Слишком бинарна. Внутри C2C (наш основной фокус) существует огромное разнообразие мотиваций, которое эта модель не улавливает. Элементы этой логики включены в `Lens_Value`.Линзы в AD-Pilot DCL — это проекции Агентов. Они инкапсулируют логику 3-осевой модели (какие оси активировать) и знания домена.


#### 4.2. Иерархия Линз и Привязка к Операциям

Система Линз в AD-Pilot организована иерархически. Классификация строится от **Операции** (момент применения) к **Роли Агента** (логика воздействия). Это обеспечивает чистоту архитектуры: инструменты формирования "Объективной Истины" отделены от инструментов создания "Субъективной Ценности".

**А. Линзы для Операции `DEFINE` (Роль: PIM-Architect)**
*Задача:* Формирование "Объективной Истины".
*Механизм:* Фильтрация. Изолирует атрибуты, необходимые для технической идентификации сущности.
*Разрешенные Линзы:*
1.  **Lens_Market_Geo** (в режиме "Standards Enforcement"). Применяется, так как технические стандарты (напряжение, частоты, разъемы) являются частью конституции товара и жестко зависят от региона.

**Б. Линзы для Операции `ENRICH` (Роль: Sociologist)**
*Задача:* Создание "Субъективной Ценности".
*Механизм:* Фокусировка. Приоритезирует атрибуты, важные для профиля потребления.
*Разрешенные Линзы:*
1.  **Lens_Market_Geo** (в режиме "Compatibility").
2.  **Lens_Market_Expertise**.
3.  **Lens_Market_Scenario**.
4.  **Lens_Market_Value**.
5.  *(Сюда же войдут Sales-линзы на следующем этапе проектирования)*.

**В. Линзы для Операции `ADAPT` (Роль: Integrator)**
*Задача:* Адаптация под Канал.
*Механизм:* Маппинг и Трансформация.
*Разрешенные Линзы:*
1.  **Lens_Channel_Tech**.
2.  **Lens_Storyteller**.


#### 4.3. Реестр Market-Линз (Функционально-Ролевая Модель)

Данный набор линз реализует принятую методологию, позволяя адаптировать схему атрибутов под 4 ключевых вектора потребления.

**1. `Lens_Market_Geo` (Где используется?)**
*   **Привязка:** `DEFINE` (Стандарты) и `ENRICH` (Совместимость).
*   **Фокус:** Физический и Культурный контекст региона.
*   **Параметры:** `Region` (напр. 'Bulgaria', 'USA'), `Category`.
*   **Логика:** Проецирует географические константы на схему.
    *   *Для DEFINE (Standards):* Фиксирует технические стандарты (Напряжение 220В, вилка Type F). Несовпадение делает товар нерабочим (L1.1 Constitutional).
    *   *Для ENRICH (Context):* Учитывает климат (жара/влага) и быт (узкие лифты). Повышает значимость атрибутов, влияющих на удобство в локальной среде (габариты, класс энергопотребления).

**2. `Lens_Market_Expertise` (Кто использует?)**
*   **Привязка:** Только `ENRICH`.
*   **Фокус:** Когнитивная нагрузка и глубина детализации данных.
*   **Параметры:** `Level` (напр. 'Pro', 'Beginner', 'Enthusiast').
*   **Логика:** Регулирует сложность и гранулярность языка описания.
    *   *Pro:* Приоритезирует "сырые факты" (L2.1 Factual). Скрывает маркетинговые упрощения, требуя конкретных метрик (тайминги RAM, графики MTF).
    *   *Beginner:* Приоритезирует сценарные подсказки (L1.3 Contextual). Снижает значимость сложных ТТХ, заменяя их на понятные метрики пользы ("Подходит для игр?", "Размывает фон?").

**3. `Lens_Market_Scenario` (Как используется?)**
*   **Привязка:** Только `ENRICH`.
*   **Фокус:** Функциональный контекст и среда эксплуатации.
*   **Параметры:** `Context` (напр. 'Gaming', 'Travel', 'Family_Safe', 'Heavy_Duty').
*   **Логика:** Определяет функциональные приоритеты и ограничения среды. Например,
    *   *Travel:* Повышает значимость мобильности (вес, габариты, автономность, прочность).
    *   *Family_Safe:* Повышает значимость безопасности (материалы, блокировки, гипоаллергенность, отсутствие мелких деталей).
    *   *Gaming:* Повышает значимость производительности (latency, fps) и эстетики (RGB, дизайн).
    *   *Heavy_Duty:* Повышает значимость надежности (IP-рейтинг, ударопрочность, ремонтопригодность).

**4. `Lens_Market_Value` (Какова мотивация?)**
*   **Привязка:** Только `ENRICH`.
*   **Фокус:** Экономическая психология и восприятие ценности.
*   **Параметры:** `Driver` (напр. 'Budget', 'Status_Luxury', 'Resale_Investment').
*   **Логика:** Определяет, какие атрибуты обосновывают цену сделки. Например,
    *   *Budget:* "Утилитарный подход". Подсвечивает дефекты, снижающие цену (царапины), и стоимость владения (расходники, ремонт).
    *   *Status_Luxury:* "Гедонистический подход". Подсвечивает бренд, материалы (L2.2 Subjective), редкость, состояние "Mint".
    *   *Resale_Investment:* "Инвестиционный подход". Подсвечивает ликвидность, сохранность заводской упаковки, документы, провенанс.

### Пример DCL-инструкций (Синтаксис)

Итоговые сценарии, демонстрирующие поток данных и разделение ответственности.

**1. Сценарий: Генерация Экспертной Схемы (Blueprint)**
```dcl
# 1. Понять, ЧТО это (Смотрим на текст)
INFER Entity('Market_Context_Fingerprint')
FROM Entity('Draft_Record')
USING Knowledge('Domain_Taxonomy')

# 2. Создать костяк (Смотрим на Фингерпринт)
DEFINE Entity('Attribute_Schema')
FROM Entity('Market_Context_Fingerprint')
USING Lens_PIM_Constitutional

# 3. Добавить маркетинговые слои (Мутируем схему)
ENRICH Entity('Attribute_Schema')
FROM Entity('Attribute_Schema')
USING Lens_Market_Persona(Target='Collector')

# 4. Добавить продажные слои (Мутируем схему)
ENRICH Entity('Attribute_Schema')
FROM Entity('Attribute_Schema')
USING Lens_Sales_Goal(Strategy='Max_Price')
```

**2. Сценарий: Извлечение Данных (Mining)**
```dcl
# Заполнить схему фактами
EXTRACT Entity('Golden_Record')
FROM Entity('Draft_Record')
USING Entity('Attribute_Schema') # Схема как трафарет
OPTIMIZING_FOR Constraint('Closed_World_Assumption')
```

**3. Сценарий: Публикация (Publishing)**
```dcl
# Адаптировать для площадки
ADAPT Entity('Channel_Listing')
FROM Entity('Golden_Record')
USING [
  Lens_Channel_Tech(Platform='Avito'),
  Lens_Storyteller(Style='Selling_Narrative')
]
```
